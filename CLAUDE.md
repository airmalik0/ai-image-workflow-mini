## Архитектура в двух абзацах

Монорепо pnpm. **Оркестрация отделена от исполнения**: API считает, у каких нод графа готовы все
зависимости, разрешает их входы и ставит job'ы в очередь; worker их выполняет, ничего не зная
о графе, и возвращает исход обратной очередью; API публикует событие в Redis pub/sub и транслирует
его в браузер через SSE и WebSocket.

Доменное ядро `packages/core` не знает про I/O: валидация графа, реактивный планировщик,
`RequestBuilder` и порты. Инфраструктура подключается адаптерами. `packages/contracts` — единственный
источник правды для типов графа, общий для фронта и бэка.

## Правила работы в этом репозитории

- **TDD по шагам плана**: красный тест → минимальная реализация → зелёный → коммит. Не «должно
  работать», а запущено и показано.
- **`packages/core` не импортирует инфраструктуру** — ни Fastify, ни Drizzle, ни BullMQ, ни `node:fs`.
  Это проверяется тестом на импорты, не на честном слове.
- **Типы графа не дублировать.** Всё из `@workflow/contracts`. Две копии контракта на фронте и бэке —
  источник рассинхронизации, а не удобства.
- Идентификаторы английские, комментарии русские. Комментировать только то, что код не объясняет сам.
- Строгий TypeScript: `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes` включены,
  `!` запрещён линтером. Относительные импорты — с расширением `.js`, типы — через `import type`.
- Перед коммитом: `pnpm format:write`, затем `pnpm lint && pnpm typecheck && pnpm test`.
- Новые решения по версиям и архитектуре — в `docs/decisions.md`.

## Принципиальные требования, которые легко потерять

Выведены из живых спайков провайдеров и разбора аналогичного решения. Каждое — место, где реализация
выглядит рабочей, не будучи таковой.

1. **Ограничение конкурентности обязательно.** Двадцать независимых генераций не должны становиться
   двадцатью одновременными запросами к провайдеру.
2. **Никакого тихого отката на заглушку** при ошибке боевого провайдера. Ошибка остаётся ошибкой,
   иначе сценарий ТЗ «нода упала → Retry» становится невоспроизводимым.
3. **Падение одной ветки не останавливает независимые.** Статус run'а считается по всем job'ам:
   пока хоть одна нода не выполнена, run не `completed`.
4. **Загрузка изображений — `multipart/form-data`**, не base64 в JSON. Иначе первая же фотография
   с телефона упирается в лимит тела запроса.
5. **У Gemini отказ модели приходит с HTTP 200** и пустым `inlineData`. Успешный HTTP — ещё не
   успешная генерация.
6. **В SSE обязательно поле `id:`**, иначе `Last-Event-ID` не работает и докачка событий существует
   только на бумаге. История не очищается при retry. Картинки в поток не идут — только `fileId`.
7. **Поля negative prompt нет ни у Gemini, ни у OpenAI.** Негатив вклеивается в текст промпта
   утвердительной формулировкой, а не списком слов через запятую — проверено эмпирически.

## Публикация

Решение владельца от 02.09.2026: в публичный репозиторий уходит **готовое решение, а не история
разработки**. Опубликовано 02.09.2026 — <https://github.com/airmalik0/ai-image-workflow-mini>,
в `main` два коммита: само решение и ссылка на демо-стенд. Локальная история детальная и ведётся как обычно — она нужна для работы
и отката; схлопывание делается один раз, перед самой публикацией:

```bash
git checkout --orphan release
git rm -r --cached .claude          # хендоффы сессий — внутренняя кухня, не для проверяющего
git add -A
git commit -m "AI Image Workflow Mini"
```

Перед этим обязательно: `git status` чист, `.env` не в индексе, `grep -r` по репозиторию не находит
ни одного ключа, все проверки зелёные (`pnpm lint && pnpm typecheck && pnpm test && pnpm e2e`).

Имя репозитория — `ai-image-workflow-mini`: на него уже настроен бейдж CI в README. Другое имя
придётся править и там.

CI проверен заранее на временном приватном репозитории `airmalik0/aiwf-ci-probe` (все три джобы
зелёные на чистом раннере). После публикации он больше не нужен и удаляется руками — у токена
`gh` нет права `delete_repo`.
