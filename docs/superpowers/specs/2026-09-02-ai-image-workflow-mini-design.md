## 1. Контекст

Тестовое задание на позицию Fullstack-разработчика в продукт **Снэпбилд** (компания «Очень»).
Исходный текст задания сохранён в `docs/task-original.html` (разделы 6–13).

Нужно построить node-based редактор workflow с реальной генерацией изображений через AI API.

### Что задание проверяет на самом деле

Три формулировки из ТЗ задают приоритеты:

1. «Полноценный визуальный Canvas **необязателен**… но graph definition, dependencies, branching и parallel execution **остаются обязательной частью**» — центр тяжести в ядре исполнения графа, не в картинке.
2. «Preset должен быть **отдельной сущностью в data model**, а не логикой, спрятанной внутри UI-компонента» — проверяют границы слоёв.
3. «**API key не должен попадать во frontend**» — проверяют базовую безопасность.

Требования вакансии (hh.ru/vacancy/136644202) дословно: TypeScript, React, Node.js, REST API, SQL-базы,
«понимание асинхронных задач, **очередей, retries и realtime-механик**». В «будет плюсом» — React Flow/xyflow,
очереди, realtime-механики и файловый storage.

Из этого следует принципиальное решение: очередь задач — не оверинжиниринг, а прямой пункт требований.

### Цели

- Закрыть **все** обязательные пункты ТЗ, включая задание со звёздочкой (Canvas).
- Показать инженерное мышление там, где ТЗ оставляет свободу: границы слоёв, порты и адаптеры, тестируемость.
- Сделать запуск тривиальным для проверяющего: одна команда, работоспособность без AI-ключа.

### Не-цели

- Мультипользовательность, аутентификация, роли.
- Полноценный Preset Editor (ТЗ прямо говорит, что он не нужен).
- Горизонтальное масштабирование в проде, кластеризация, observability-стек.

## 2. Обзор архитектуры

Монорепо на pnpm workspaces:

```
apps/
  web/          Vite + React + TypeScript, Feature-Sliced Design, @xyflow/react
  api/          Fastify — REST, SSE, WebSocket, оркестрация графа
  worker/       исполнитель job'ов (тот же образ, другая команда)
packages/
  contracts/    zod-схемы и типы: граф, DTO, события. Изоморфный пакет.
  core/         доменное ядро: валидация графа, планировщик, RequestBuilder. Без I/O.
```

### Почему ядро отдельным пакетом

`packages/core` не импортирует ни Fastify, ни Drizzle, ни BullMQ, ни fetch. Он оперирует чистыми
структурами и портами. Следствия:

- unit-тесты ядра идут за миллисекунды, без Docker и без сети;
- одна и та же валидация графа переиспользуется на фронте (мгновенная обратная связь) и на бэке
  (единственная точка, которой можно доверять);
- смена БД, очереди или AI-провайдера не трогает домен.

### Поток выполнения

```
POST /api/runs
      │
      ▼
  Orchestrator ──── создаёт Run + Jobs (все idle)
      │
      ├─ считает готовые ноды: те, у кого ВСЕ входные зависимости в статусе success
      ├─ ставит их в очередь BullMQ                              → job.status = queued
      │
      ▼
   Redis (queue: jobs, pub/sub: run-events)
      │
      ▼
  Worker ×N (concurrency = WORKER_CONCURRENCY)
      ├─ резолвит входы job'а из результатов предшественников
      ├─ RequestBuilder(userPrompt, preset, params) → ProviderRequest
      ├─ ImageProvider.generate/edit(request, signal)            → job.status = running
      ├─ FileStorage.put(bytes) + запись в Postgres
      └─ публикует событие в Redis pub/sub                       → success | error
      │
      ▼
  Orchestrator (подписан на события)
      ├─ пересчитывает готовность → ставит следующую волну
      └─ либо закрывает run: completed | failed | cancelled
      │
      ▼
  API транслирует события в браузер: SSE (основной) и WebSocket (альтернативный транспорт)
```

Ключевое разделение: **оркестрация** знает про граф и зависимости, **исполнение** не знает про граф вообще.
Worker получает самодостаточный job и не догадывается, что он часть DAG. Это позволяет масштабировать
исполнение независимо и делает обе части тестируемыми по отдельности.

## 3. Доменная модель

### 3.1 Граф

```ts
type PortType = 'text' | 'image'

type NodeKind =
  | 'prompt'          // out: text
  | 'imageInput'      // out: image
  | 'generateImage'   // in: text (required)                  → out: image
  | 'editImage'       // in: image (required), text (optional) → out: image
  | 'result'          // in: image (required)

interface WorkflowNode {
  id: string
  kind: NodeKind
  position: { x: number; y: number }
  data: NodeData          // дискриминированное объединение по kind
}

interface WorkflowEdge {
  id: string
  source: string; sourceHandle: string
  target: string; targetHandle: string
}

interface WorkflowGraph {
  nodes: WorkflowNode[]
  edges: WorkflowEdge[]
}
```

Описание портов каждой ноды задаётся **декларативно**, в одной таблице `NODE_SPECS`:

```ts
const NODE_SPECS: Record<NodeKind, NodeSpec> = {
  generateImage: {
    inputs:  { prompt: { type: 'text', required: true } },
    outputs: { image:  { type: 'image' } },
    params: /* zod-схема параметров: presetId, model, aspectRatio, ... */
  },
  // ...
}
```

Из этой таблицы выводится всё: правила соединения на канвасе, серверная валидация, форма инспектора,
резолв входов в воркере. Добавить новый тип ноды — значит добавить строку в `NODE_SPECS` и один рендерер.

### 3.2 Preset

Отдельная сущность в БД, как прямо требует ТЗ.

```ts
interface Preset {
  id: string
  name: string
  mainPrompt: string
  negativePrompt: string | null
  references: string[]        // id файлов в FileStorage
  defaults: { model?: string; aspectRatio?: string } | null
  createdAt: Date
  updatedAt: Date
}
```

Нода `generateImage` хранит **только `presetId`**, а не копию содержимого. Пресеты сеются миграцией
и доступны через REST (`GET /api/presets`, CRUD).

### 3.3 Run и Job

```ts
type JobStatus = 'idle' | 'queued' | 'running' | 'success' | 'error' | 'skipped'
type RunStatus = 'queued' | 'running' | 'completed' | 'failed' | 'cancelled'

interface Job {
  id: string
  runId: string
  nodeId: string
  status: JobStatus
  attempt: number
  startedAt: Date | null
  finishedAt: Date | null
  output: JobOutput | null      // { type: 'text', value } | { type: 'image', fileId }
  error: JobError | null        // { code, message, retryable }
}
```

**Отступление от ТЗ, сделанное сознательно.** ТЗ перечисляет пять статусов job'а. Добавлен шестой —
`skipped`, для нод, которые не будут выполнены, потому что упал их предок. Помечать такую ноду как `error`
означало бы врать: ошибки в ней не было. Пять статусов ТЗ остаются каноном, `skipped` — расширение,
и оно отмечено в README.

Статусы run'а взяты из ТЗ дословно (`queued / running / completed / failed`), плюс `cancelled`.

## 4. Алгоритмы

### 4.1 Валидация графа

Выполняется в `packages/core`, вызывается и на фронте, и на бэке. Проверки:

| Проверка | Правило |
|---|---|
| Схема | zod: структура, известные `NodeKind`, ссылочная целостность рёбер |
| Типы портов | `text` соединяется только с `text`, `image` только с `image` |
| Арность | у входного порта не более одного источника; выход может ветвиться свободно |
| Циклы | DFS с тремя цветами; в сообщении возвращается сам цикл |
| Обязательные входы | все `required`-порты подключены |
| Достижимость | нода не участвует в путях, ведущих к `result` → предупреждение, не ошибка |
| Наличие терминала | хотя бы одна `result`-нода → иначе ошибка |

Результат: `{ errors: ValidationIssue[], warnings: ValidationIssue[] }`, где у каждой проблемы есть
`nodeId`/`edgeId` — фронт подсвечивает именно виновника.

### 4.2 Планировщик

Не «уровни» и не `Promise.all` по слоям. Планировщик реактивный:

```
ready(run) = { job | job.status === 'idle'
                     ∧ ∀ dep ∈ deps(job): dep.status === 'success' }
```

Пересчитывается при каждом изменении статуса. Это важнее, чем кажется: при волновой схеме быстрая
ветка ждёт медленную из своей волны, хотя её потомки уже могли бы стартовать. Реактивный планировщик
запускает ноду в тот момент, когда готовы именно её зависимости.

Если предок упал — весь его транзитивный «конус потомков» получает `skipped`, обход в ширину.

Run считается завершённым, когда нет job'ов в `idle`, `queued` или `running`.
`failed`, если хотя бы один в `error`; иначе `completed`.

### 4.3 Параллелизм и его доказательство

Параллелизм обеспечивается воркерами: BullMQ с `concurrency = N` (по умолчанию 4), возможен запуск
нескольких контейнеров-воркеров.

**Ограничение конкурентности обязательно и проверяется тестом.** Граф из двадцати независимых
генераций не должен превращаться в двадцать одновременных запросов к провайдеру: у AI-провайдеров
жёсткие лимиты (у fal на новом аккаунте — два параллельных запроса), и «параллелизм» без потолка
означает шквал 429 вместо ускорения. Потолок задаётся `MAX_CONCURRENT_JOBS`.

**Падение одной ветки не останавливает независимые.** Ошибка гасит только транзитивный конус
потомков упавшей ноды; соседние ветки доводятся до конца. Статус run'а считается по **всем** job'ам,
а не по факту завершения обхода: если хоть одна нода осталась невыполненной, run не может быть
`completed`.

Доказывается двумя способами, не требующими чтения кода:

1. **Тест**, который валит сборку: граф с двумя независимыми ветками, fake-провайдер с задержкой 200 мс
   на генерацию; общее время run'а должно быть меньше 350 мс. При последовательном исполнении — от 400 мс.
2. **Run Timeline** в UI: диаграмма Ганта по `startedAt`/`finishedAt` каждого job'а. Перекрытие полос
   `Generate A` и `Generate B` видно глазами.

### 4.4 Retry

Два разных механизма, которые нельзя путать:

- **Автоматический** — внутри BullMQ, для транзиентных ошибок (HTTP 429, 5xx, таймаут, сетевой сбой):
  3 попытки, экспоненциальный backoff с джиттером. Ошибки валидации и safety-блокировки не ретраятся —
  они помечены `retryable: false`.
- **Ручной** — `POST /api/runs/:runId/nodes/:nodeId/retry`. Сбрасывает выбранную ноду и её конус потомков
  в `idle` и запускает планировщик заново. Успешные предки **не пересчитываются**: их выходы уже сохранены.

### 4.5 Отмена

`POST /api/runs/:runId/cancel` выставляет флаг в Redis, снимает из очереди ещё не начатые job'ы, а
работающим воркерам сигналит через `AbortSignal`, который прокинут до `fetch` к провайдеру.

Базовый префикс `/api`. Все тела запросов и ответов описаны zod-схемами из `packages/contracts`,
из них же генерируется OpenAPI (`/api/docs`).

```

GET    /api/presets                             → Preset[]
POST   /api/presets                             → Preset
GET    /api/presets/:id
PATCH  /api/presets/:id

GET    /api/workflows                           → сохранённые графы
POST   /api/workflows

PUT    /api/workflows/:id

GET    /api/runs                                → история запусков
GET    /api/runs/:runId                         → { run, jobs[] }  ← polling-фолбэк
GET    /api/runs/:runId/events                  → SSE, поддерживает Last-Event-ID
POST   /api/runs/:runId/cancel
POST   /api/runs/:runId/nodes/:nodeId/retry

POST   /api/files                               → загрузка изображения → { fileId, url }
```

Ошибки — единый конверт: `{ error: { code, message, details? } }`, коды машиночитаемые
(`GRAPH_INVALID`, `PROVIDER_RATE_LIMITED`, `PROVIDER_SAFETY_BLOCKED`, `RUN_NOT_FOUND`, …).

## 6. Realtime

Источник истины — Redis pub/sub, канал на run. Воркер публикует, API-инстансы подписаны.
Это не роскошь: воркер — отдельный процесс, и без общей шины API просто не узнает о прогрессе.

Наружу — два транспорта за одним интерфейсом:

- **SSE** `GET /api/runs/:runId/events` — основной. Браузер сам переподключается, а `Last-Event-ID`
  позволяет докачать пропущенные события: каждое событие имеет монотонный `seq` в пределах run'а.
- **WebSocket** `/api/ws?runId=…` — тот же поток. Сделан потому, что в требованиях вакансии realtime
  стоит отдельным пунктом, а SSE односторонний: WS оставляет дорогу для обратного канала.
- **Polling** `GET /api/runs/:runId` — работает всегда, документирован как фолбэк.

События: `run.started`, `job.updated`, `run.finished`.

Требования, без которых SSE ломается на практике:

- у каждого события проставляется поле `id:` — иначе браузер не пришлёт `Last-Event-ID`, и заявленная
  докачка не работает;
- история событий run'а хранится кольцевым буфером и **не очищается при retry** — иначе клиент,
  подключившийся позже, никогда не узнает, что нода падала;
- периодический heartbeat-комментарий, чтобы соединение не резалось прокси по таймауту простоя;
- **изображения в поток не попадают** — событие несёт `fileId`, картинка забирается отдельным
  запросом. Base64 в SSE раздувает трафик и память на каждом переподключении.

## 7. Провайдеры изображений

```ts
interface ImageProvider {
  readonly id: string
  readonly models: ModelDescriptor[]
  readonly capabilities: {
    edit: boolean
    referenceImages: number      // сколько референсов принимает; 0 — не поддерживает
    negativePrompt: boolean
    aspectRatio: string[]
  }
  generate(req: GenerateRequest, signal: AbortSignal): Promise<ProviderImage>
  edit(req: EditRequest, signal: AbortSignal): Promise<ProviderImage>
}
```

Реализации:

| id | Назначение |
|---|---|
| `openai` | боевой: `gpt-image-2`, text→image, image+text→image, несколько референсов одним запросом |
| `gemini` | боевой: `gemini-3.1-flash-image`, те же три операции |
| `fake` | детерминированный, рисует изображение локально; управляемая задержка и управляемые сбои |

Оба боевых провайдера проверены живыми запросами до начала реализации: генерация, редактирование
и передача двух референсов одним запросом. Кода, который ни разу не выполнялся, в решении нет.

`fake` — не заглушка ради тестов, а страховка для проверяющего: `IMAGE_PROVIDER=fake docker compose up`
поднимает полностью рабочее приложение без всякого AI-ключа. Он же используется в unit-, интеграционных
и E2E-тестах, поэтому CI не зависит от внешнего API и не жжёт квоту.

**`fake` включается только явным выбором.** Никакого тихого отката на заглушку при ошибке боевого
провайдера: ошибка обязана оставаться ошибкой. Молчаливая подмена делает неработающим главный сценарий
ТЗ — «нода упала, нажми Retry», — потому что упасть становится нечему, и заодно обманывает того,
кто смотрит на результат.

Ошибки провайдеров нормализуются в единый `ProviderError { code, message, retryable }` — воркер и BullMQ
принимают решение о повторе по флагу `retryable`, а не по тексту ошибки. Отдельно учитывается,
что у Gemini отказ модели приходит с HTTP 200 и пустым `inlineData`: успешный HTTP — ещё не успешная
генерация.

### Матрица возможностей

Провайдеры и модели различаются не косметически: у Gemini и OpenAI нет отдельного поля negative prompt,
у Wan оно есть; где-то референсы передаются массивом изображений, где-то одиночным полем; наборы
поддерживаемых пропорций не совпадают. Поэтому `capabilities` — не декоративное поле: `RequestBuilder`
по нему деградирует (негатив вклеивается в текст промпта, лишние референсы отсекаются), а UI гасит
неподдерживаемые настройки с пояснением, вместо того чтобы принимать значение и молча его терять.

### RequestBuilder

Чистая функция, буквальный ответ на требование ТЗ про Preset:

```ts
buildProviderRequest(input: {
  userPrompt: string
  preset: Preset | null
  nodeParams: GenerateParams
}): ProviderRequest
```

Правила слияния: `mainPrompt` пресета и пользовательский промпт склеиваются в заданном порядке;
`negativePrompt` берётся из пресета и дополняется; `references` пресета передаются как изображения;
`defaults` пресета перекрываются явными параметрами ноды. Всё это покрыто unit-тестами — никакого
доступа к сети для их запуска не нужно.

## 8. Хранилища

**Postgres + Drizzle.** Таблицы: `presets`, `workflows`, `runs`, `jobs`, `files`.
Миграции — `drizzle-kit`, сид пресетов и референсных картинок при первом старте.
Доступ к данным — через порты-репозитории; в тестах ядра подставляется in-memory реализация.

**FileStorage** — порт с двумя адаптерами:

- `fs` (по умолчанию) — каталог в volume, отдача через `GET /api/files/:id`;
- `s3` — любое S3-совместимое хранилище, для демо-стенда.

S3-адаптер существует не для галочки: «файловый storage» — отдельный пункт в требованиях вакансии,
а демо-стенд крутится на эфемерной файловой системе, где локальный диск не переживает рестарт.

**Загрузка изображений идёт через `multipart/form-data` на отдельный эндпоинт, а не base64 в JSON-теле.**
Разница не стилистическая: base64 распухает на треть и упирается в лимит размера тела, из-за чего
загрузка обычной фотографии с телефона проваливается с ошибкой «request entity too large». Нода
`imageInput` хранит `fileId`, а не содержимое файла. Лимит размера задаётся явно и проверяется тестом
на файле реального размера, а не на иконке.

```
              select-preset, select-model, upload-image
  entities/   workflow, node, preset, run, job — модели и презентационные компоненты
  shared/     api (клиент + SSE/WS), ui (кнопки, поля, пилюли), lib, config
```

Правило импорта — только «сверху вниз», проверяется линтером (`eslint-plugin-boundaries`), а не
на словах. Публичный API слайса — через `index.ts`.

Ключевая дисциплина, ради которой ТЗ и просит FSD: бизнес-логика живёт в `entities`/`features` и в
`packages/core`, компоненты в `widgets` только рисуют. В частности, ни один React-компонент не знает,
как пресет превращается в запрос к провайдеру.

### Состояние

- Граф — Zustand-стор в `entities/workflow`, React Flow в контролируемом режиме.
- Серверные данные — TanStack Query; SSE-подписка не дублирует стор, а прицельно обновляет кэш query.

### Валидация соединений на канвасе

`isValidConnection` React Flow вызывает ту же функцию из `packages/core`, что и сервер. Несовместимый
порт не соединяется, курсор показывает запрет. Но сервер всё равно валидирует граф заново: фронту
доверять нельзя.

## 10. UI

Смотреть будет дизайн-агентство, поэтому интерфейс не «функциональный», а нарисованный.

Раскладка — три колонки: палитра нод слева, канвас в центре, инспектор справа. Снизу — выдвижной
Run Timeline. Тёмная тема, точечная сетка канваса, один акцентный цвет, статус-пилюли на нодах,
скруглённые карточки нод с чипами модели и пресета внутри ноды `generateImage`, счётчик символов
в промпте.

Состояния, которые обязаны быть видимыми: `idle` / `queued` / `running` (прогресс) / `success` /
`error` (с текстом и кнопкой Retry прямо на ноде) / `skipped` (приглушённая нода).

Три готовых сценария в один клик — ровно те, что нарисованы в ТЗ: линейная генерация, редактирование
изображения и обязательное ветвление одного промпта в две параллельные генерации.

## 11. Тестирование

| Уровень | Инструмент | Что покрывается |
|---|---|---|
| Unit, ядро | Vitest | валидация (циклы, типы, арность, достижимость), планировщик (ромб, ветвление, конус пропуска), RequestBuilder (слияние пресета), нормализация ошибок провайдера |
| Unit, параллелизм | Vitest | тайминговый тест: две ветки по 200 мс укладываются в 350 мс |
| Интеграция, API | Vitest + `fastify.inject` | полный прогон run на `fake`-провайдере, SSE-поток, retry, cancel, коды ошибок |
| E2E | Playwright | собрать граф с ветвлением в UI, запустить, дождаться двух результатов, уронить ноду и нажать Retry |
| Ручная проверка | — | одна реальная генерация через Gemini, скриншот в README |

CI (GitHub Actions): lint → typecheck → unit → build → интеграционные и E2E на `fake`-провайдере.
Внешние ключи в CI не нужны.

## 12. Запуск

```bash
cp .env.example .env       # ключ не обязателен
docker compose up          # http://localhost:3000
```

Compose поднимает: `postgres`, `redis`, `api`, `worker`, `web`. Миграции и сид — автоматически,
через healthcheck-зависимости. Без `GEMINI_API_KEY` приложение стартует на `fake`-провайдере и
полностью работоспособно; об этом сказано в README первой строкой.

Демо-стенд — одна ссылка в README, на `fake`-провайдере либо с жёстким рейт-лимитом, чтобы чужие
запросы не сожгли квоту.

## 13. Что сознательно не делается

Каждый пункт попадёт в README, чтобы отсутствие читалось как решение, а не как недоделка.

- **Аутентификация и мультипользовательность** — вне рамок ТЗ.
- **Preset Editor** — ТЗ прямо говорит, что он не нужен; сделан CRUD по API и выбор в UI.
- **Собственный canvas-engine** — ТЗ прямо говорит не писать с нуля.
- **Версионирование пресетов и промптов** — интересно продукту, но за рамками задания.
- **Observability-стек** (метрики, трейсинг) — есть структурные логи с `runId`/`jobId`, дальше не идём.
- **Kubernetes, автоскейлинг** — вместо этого объяснено, как воркер масштабируется репликами.
